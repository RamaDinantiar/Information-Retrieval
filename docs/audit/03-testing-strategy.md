# Audit Pra-Deploy — Strategi Test

Peta cakupan test yang ada dan rencana penambahan. **Tahap ini hanya rencana.** Test baru ditulis setelah Anda menyetujui, dan kode aplikasi tidak diubah: semua test harus lolos dengan kode saat ini.

> Penomoran: berkas ini bernama `03-testing-strategy.md`. Dokumen berikutnya dalam urutan: `04-tech-debt.md`, `05-webapp-testing.md`, `06-deploy-checklist.md`. (`03-checklist-deploy.md` yang lama tetap ada; checklist final nanti ditulis ulang sebagai `06-deploy-checklist.md`.)

- **Basis:** `main` @ `0944e0e`; 554 test lolos pada akhir audit, sekitar 10.000 baris di `tests/`
- **Isi `tests/`:** hanya PHP (Pest/PHPUnit, SQLite in-memory). Tidak ada test komponen TypeScript dan tidak ada test E2E browser.
- **Driver coverage:** tidak terpasang (`pcov`/`xdebug` tidak ada), jadi angka persen coverage tidak bisa diukur. Peta di bawah dibuat dari tiga sumber: (1) 183 rute dibandingkan dengan nama rute yang muncul di `tests/`, (2) kelas di `app/Actions`, `app/Support`, `app/Http/Middleware`, `app/Jobs` yang tidak disebut di test mana pun, (3) daftar nama test per area. Metode ini **pendekatan**: rute yang diuji lewat URL tertulis (bukan `route('nama')`) atau kelas yang diuji lewat HTTP bisa terhitung "tidak tercakup" padahal ada efek tidak langsung. Setiap butir di bawah ditandai **terverifikasi** (saya membaca kodenya) atau **perlu dicek** (saya hanya melihat nama test).

## 1. Ringkasan

Cakupan fitur utama sudah luas. Rekap Jam Ngawas paling tebal (sekitar 150 test, termasuk fixture emas April 2026). Celahnya bukan "fitur tanpa test", melainkan empat pola:

1. **Tidak ada pemeriksaan RBAC yang sistematis.** Hak akses diuji satu per satu di sekitar 30 berkas. Rute baru yang lupa diberi middleware `role:` tidak akan ketahuan oleh test mana pun.
2. **29 rute tidak pernah disebut di test**, sebagian di area sensitif (unduh isi ZIP submission, rute login `dev/login-as`).
3. **Logika murni tanpa test unit.** Hanya satu berkas di `tests/Unit` yang berisi test sungguhan (`NimFormatterTest`). `FinalScore`, `JoinToken`, `ZipBrowser`, `ClassDays`, `AssistantWeek`, `GradingQueue` hanya tersentuh lewat HTTP.
4. **Cabang gagal dan batas nilai** (null, nol, tepat di batas, input berlebih) lebih jarang diuji daripada jalur sukses.

## 4. Target

Karena coverage tidak terukur, targetnya berupa **kriteria selesai**, bukan persen:

- Setiap rute berawalan `admin/`, `asisten/`, `praktikan/` terkena matriks RBAC (P0-1) dan tidak ada rute baru yang lolos tanpa `role:` (P0-2).
- Setiap rute pada daftar 29 punya sekurang-kurangnya satu test sukses dan satu test penolakan, atau alasan tertulis mengapa dikecualikan (Program: nonaktif; `dev.login-as`: P0-3).
- Setiap metode publik `FinalScore`, `JoinToken`, `ZipBrowser`, `ClassDays`, `AssistantWeek` punya test unit dengan nilai batas.
- Setelah P3-1: target awal 80% baris untuk `app/Actions` dan `app/Support`, 70% untuk `app/Http/Controllers`. Angka ini usulan, bukan hasil ukur.

## 5. Yang sengaja tidak dites

- Kode framework dan paket (Fortify, Inertia, PhpSpreadsheet).
- Tampilan visual dan kelas Tailwind.
- Modul Program: dinonaktifkan (`LAB_PROGRAMS_ENABLED=false`) dan belum ditinjau audit. Test yang ada (`ProgramTest`, `ProgramUnavailableTest`) dibiarkan; rute `asisten.programs.show/update` tidak ditambah test sampai modul ditinjau.
- Beban dan kinerja nyata (S8, R3): butuh pengukuran di server sungguhan, bukan test otomatis. Yang masuk hanya penjaga N+1 pada P1-8.
- Frontend dan E2E: tidak masuk tahap ini. Risiko di lapisan itu (validasi sisi klien, tampilan galat) tetap hanya tertutup uji manual di checklist D.

## 6. Aturan penulisan tahap berikutnya

1. **Kode aplikasi tidak diubah.** Semua test harus hijau pada kode saat ini.
2. **Bila test mengungkap bug:** jangan ubah kode dan jangan menulis test yang mengunci perilaku salah. Catat temuannya di bagian "Temuan baru" berkas ini (rute, input, perilaku, usulan perbaikan), lalu tunggu keputusan Anda. Test untuk perilaku yang salah itu tidak di-commit sampai kodenya diperbaiki.
3. **Test harus bisa gagal.** Untuk P0 dan P1 saya buktikan dengan merusak kode secara sementara (mis. hapus `role:` dari satu rute, hapus `abort_unless` di `zipFile`) dan memastikan test gagal, lalu mengembalikan kodenya. Perusakan itu tidak di-commit. Ini satu-satunya saat kode disentuh, dan hanya di salinan kerja sementara.
4. **Behavioral, bukan isi berkas.** Seperti pelajaran dari audit: hindari test yang hanya membaca teks kode atau mock internal.
5. **Tahap per tahap:** P0 → jalankan `php artisan test`, PHPStan, Pint → commit → P1 → dst. Satu commit per kelompok prioritas, di branch `test/coverage-gaps`, PR terpisah.
6. Konvensi sesuai yang ada: `RefreshDatabase`, factory `User::factory()->admin()/asisten()/praktikan()`, trait `BuildsNgawasRecaps` untuk data rekap.

## 8. Keputusan (sudah diambil)

1. Urutan P0 → P1 → P2, **satu commit per prioritas**. P0 dan P1 wajib selesai sebelum deploy; P2 bila waktu cukup. P3 ditunda, kecuali pcov.
2. Nama berkas `03-testing-strategy.md`.
3. Branch `test/coverage-gaps` dari `main` terbaru, satu PR.
4. Skala huruf mutu: diambil dari **satu sumber** (konstanta di `FinalScore`), ditandai "ASUMSI S9 – menunggu skala resmi IT PLN" di sumber dan di test, dan dicatat di Temuan baru. Test tidak menulis ulang angka batas.
5. pcov dipasang di CI hanya untuk menampilkan laporan coverage, **tanpa batas minimum** supaya CI tidak gagal.
